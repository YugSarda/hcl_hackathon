========================================================================
UNRESOLVED BUSINESS QUESTIONS & ASSUMPTIONS
========================================================================
1. Day 1 products.json is malformed (JSON parse error at line 41, col 3).
   No Day 1 products table exists in Bronze, so Day 1 transactions CANNOT be
   checked for UNKNOWN_PRODUCT_ID referential integrity. Those checks are
   skipped for Day 1 transactions. This is a known gap, not a data error.

2. account_id referential integrity (transactions.account_id ->
   customers.account_id) is treated as a WARNING, not a hard error, because
   an account may exist in the banking system without appearing in this
   particular customer extract.

3. Each day is treated as an independent batch for referential integrity.
   Day 2 transactions are validated against Day 2 branches/products only.

4. Negative transaction amounts are flagged as a WARNING (NEGATIVE_AMOUNT),
   not rejected. The data does not establish whether negative amounts mean
   refunds, errors, or legitimate adjustments. Refund handling requires a
   documented business rule before it can be enforced as a hard error.

5. Transaction status variations (e.g. 'Faild', 'Succes', 'pending') are
   flagged as INCONSISTENT_STATUS_CASE warnings. No status value is rejected
   because the valid status set is not formally documented in the source.

6. Malformed JSON (Day 1 products.json) is never repaired. The source file
   remains unchanged. It must be fixed at the source and re-ingested.

Reproducibility: Rerunning Step 3 replaces all Silver tables (full refresh),
producing identical results from the same Bronze input.
